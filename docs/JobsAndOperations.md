# Society 공통 작업 모델 명세

모델 가져오기의 실행 서비스, 항목별 이력과 재시도는 iiSocietyContainer에 있다.
macOS와 Linux에서는 Society 상주 백엔드가 이를 소유하고 화면이 로컬 채널로 상태를
표시한다. 화면이 닫혀도 백엔드가 살아 있는 동안 수용된 모델 작업은 계속 실행된다.
작업 이력은 프로세스 재시작 후 조회할 수 있으나 중단된 항목을 무조건 자동 재실행하지
않는다. 그 밖의 작업 종류와 Windows·모바일에 같은 수명 보장을 일괄 적용하지 않는다.

모델 요청의 응답이 끊기거나 제한 시간 안에 확인되지 않으면 화면은 작업의 성공이나
실패를 추정하지 않는다. 대기 상태를 해제하고 작업 이력을 먼저 확인하도록 안내하며,
사용자의 중복 요청을 방지하기 위해 결과가 불확실한 명령을 자동으로 다시 보내지 않는다.
백엔드는 기존 Society 작업 저장 위치를 그대로 사용한다.

## 목적과 적용 상태

이 문서는 Society의 작업에 대한 **목표 제품 계약**이다. 작업에 관한 현재 구현은
[기존 구현과 이행 경계](#기존-구현과-이행-경계)에서 구분하며, 이 문서가 모든
작업 유형의 구현이나 백그라운드 실행을 보장하는 것은 아니다.

**작업은 UI의 로딩 표시와 독립적으로 존재한다.** 화면은 작업의 상태를 조회하고
표시하는 관찰자이며, 화면 전환·뷰 제거·진행 창 닫기는 그 자체로 작업의 성공,
실패 또는 취소가 아니다. 사용자가 다른 화면으로 이동했다 돌아와도 실행 소유자가
살아 있는 작업은 같은 작업을 다시 확인할 수 있어야 한다.

## 적용 대상

동일한 작업 식별·상태·진행·결과·제어 계약을 다음 기능에 적용한다. 공통 모델을
쓴다는 것은 모든 기능이 같은 작업자 프로세스나 같은 구현을 사용해야 한다는 뜻이
아니다. 각 기능의 실제 수행과 결과 검증은 해당 기능을 소유한 SDK 또는 제공자가
담당한다.

- 작업 예: 대용량 업로드·다운로드; 입력과 결과의 예: 지정 판본과 출발·도착 위치 → 대상 사본; 성공을 판단할 범위: 작업이 약속한 전송·검증의 완료. 전송만 하는 하위 단계와 검증을 포함한 작업은 구분한다.
- 작업 예: 기기 간 복제; 입력과 결과의 예: 자원·판본과 대상 기기 → 해당 기기의 사본; 성공을 판단할 범위: 대상 판본의 적용과 해당 작업이 약속한 확인. 다른 기기나 더 새로운 편집까지 완료되었다는 뜻은 아니다.
- 작업 예: 외부 자료 가져오기; 입력과 결과의 예: 명시한 출처와 가져오기 조건 → 새로 등록된 자원 또는 사본; 성공을 판단할 범위: 실제 가져오기와 작업이 약속한 등록 결과. 원본 보존과 기존 자원의 정체성은 별도 계약을 따른다.
- 작업 예: 썸네일 생성; 입력과 결과의 예: 자원·대상 판본과 프리뷰 조건 → 해당 판본의 프리뷰; 성공을 판단할 범위: 지정 입력에 대한 프리뷰 생성·게시. 원본이 다른 위치에 있거나 보존되었다는 뜻은 아니다.
- 작업 예: 파일 검사와 색인; 입력과 결과의 예: 검사 범위와 대상 상태 → 검사 결과 또는 검색 색인; 성공을 판단할 범위: 약속한 범위의 검사·색인 게시. 색인이 원본이나 별도 복구 지점을 대신하지 않는다.
- 작업 예: 프로젝트 패키징; 입력과 결과의 예: 프로젝트 정의와 지정 리소스·판본 → 패키지; 성공을 판단할 범위: 작업이 약속한 입력 확인과 패키지 생성·게시. 프로젝트 참조와 배포본 확정은 별개이다.
- 작업 예: 배포본 준비; 입력과 결과의 예: 명시된 자원·판본과 준비 조건 → 배포 후보 또는 확정된 릴리스; 성공을 판단할 범위: 해당 작업이 약속한 준비 또는 확정. 게시·공개·원격 보존은 별도 작업이나 단계로 표시한다.

작업은 필요에 따라 단계나 하위 작업으로 구성한다. 예를 들어 원격 사본 배치에는
전송과 대상 검증 단계가 있을 수 있다. 전송 단계의 성공을 전체 배치 작업의 성공으로
표시하지 않는다. 자원·판본·사본과 세 가지 완료 경계는
[자원 정체성 및 보존 상태 명세](ResourceIdentityAndProtection.md)를 따른다. 복제와
별도 보존 정책의 백업·복구는 [복구와 보존 명세](VersionTrashReplicaBackup.md)를
따른다.

## 작업의 정체성과 정보

각 작업은 최소한 다음 정보를 표현할 수 있어야 한다. 이것은 모델의 의미이며 현재
저장 스키마, API 이름 또는 화면 구성을 확정한 것은 아니다.

- 정보: 작업 ID와 종류; 의미: 화면 인스턴스나 프로세스 ID와 별개로 작업을 식별한다.
- 정보: 요청자; 의미: 요청 주체, 필요한 위임 관계와 권한 범위를 구분한다.
- 정보: 대상 자원과 기준 판본; 의미: 대상 자원 ID와 작업에 적용되는 기준 판본을 지정한다. 대상이 여러 개이거나 기준이 아직 없으면 그 사실을 표현한다.
- 정보: 실행 노드와 실행 소유자; 의미: 배정된 기기·노드, 실제 실행한 노드와 그곳의 앱 서비스·데몬·플랫폼 실행 주체를 구분한다. 아직 정해지지 않았으면 미정으로 둔다.
- 정보: 상태와 현재 단계; 의미: 전체 작업 상태와 현재 실행 단계, 대기·중단 이유를 구분한다.
- 정보: 처리량과 진행 정보; 의미: 처리한 항목·바이트·전체량·단위, 측정된 처리 속도와 관찰 시각을 기록한다. 알 수 없는 값은 미상으로 둔다.
- 정보: 항목별 결과; 의미: 각 입력 항목의 식별자, 상태, 성공 결과 또는 실패 단계·원인과 재시도 가능 여부를 구분한다.
- 정보: 체크포인트; 의미: 지정 입력과 시도에 대응하는 마지막으로 안전하게 보존된 처리·검증 지점을 기록한다.
- 정보: 산출물과 오류; 의미: 만들어진 결과의 참조·대상 판본·게시 상태와 실패 이유를 구분한다.
- 정보: 재시도 횟수와 시도 관계; 의미: 전체 작업과 필요한 경우 각 항목의 시도·재시도 횟수 및 원래 요청과의 관계를 기록한다.
- 정보: 취소 가능 여부; 의미: 현재 단계에서 취소를 요청할 수 있는지, 요청과 실제 중단이 확인되었는지를 구분한다.
- 정보: 수명과 복구 정책; 의미: 뷰 종료, 앱 종료, 기기 재시작 및 플랫폼 중단에 대해 어떤 행동을 보장하는지 구분한다.

여러 입력에 대한 작업은 항목별로 안정적인 작업 내 식별자를 부여한다. 같은 이름이나
같은 내용의 별도 입력을 하나의 결과로 합치지 않는다. 항목의 성공·실패·미처리·취소와
결과 확인이 필요한 상태를 구분하며, 집계 수치는 현재 항목별 상태를 기준으로 산출한다.
재시도 기록은 이전 시도 결과를 보존하되 같은 항목을 전체 대상 수에 중복 합산하지 않는다.

작업은 목록과 상세 조회에서 같은 ID로 찾을 수 있어야 한다. 가능한 경우 동일 작업을
여러 화면이나 에이전트가 동시에 관찰할 수 있으며, 한 관찰자의 구독 종료는 다른
관찰자나 작업 자체를 종료하지 않는다. 상태 알림이 유실되거나 새 화면이 열려도 현재
상태를 다시 조회할 수 있어야 한다. 알림 전달 자체를 완료의 근거로 삼지 않는다.
장치 화면에서의 실행 주체·대상 위치와 그 상태는
[장치 상태와 기능 명세](DeviceStateAndCapabilities.md)를 따른다.

## 상태와 진행 표시

작업의 공통 상태는 사용자에게 무엇이 일어났는지와 다음 행동을 설명한다.

- 상태: 대기; 표시해야 할 내용: 작업이 무엇을 기다리는지와 알려진 다음 조건
- 상태: 노드 대기; 표시해야 할 내용: 실행 또는 접근에 필요한 기기·노드와 연결 상태; 대상을 모르면 미확인으로 표시
- 상태: 권한 대기; 표시해야 할 내용: 부족하거나 확인할 수 없는 접근 행위와 대상, 가능한 해결 방법
- 상태: 일시 중단; 표시해야 할 내용: 중단된 단계와 알려진 재개 조건
- 상태: 진행; 표시해야 할 내용: 현재 단계, 처리한 항목·양과 알려진 전체량
- 상태: 일부 완료; 표시해야 할 내용: 성공·실패한 항목과 수, 각 결과와 다시 처리할 수 있는 범위
- 상태: 실패; 표시해야 할 내용: 실패 원인·단계와 재시도 가능한 항목 또는 범위
- 상태: 취소됨; 표시해야 할 내용: 실제 중단된 범위와 이미 완료·게시된 결과, 처리되지 않은 항목
- 상태: 성공; 표시해야 할 내용: 해당 작업이 약속한 단계와 결과가 확인되었는지

노드·권한 대기는 필요한 경우 일반 대기의 구체적인 이유로 표현할 수 있으나,
사용자는 어느 기기나 접근이 필요한지 구분할 수 있어야 한다. 여러 항목의 처리가
진행 중일 때 성공과 실패가 함께 관찰되더라도 아직 수행할 작업이 남았다면 진행
상태와 그 결과를 함께 표시한다. 처리가 끝나 성공과 실패가 공존하면 일부 완료로
표시한다. 취소된 작업에서 이미 성공한 항목이 있다면 취소 상태와 성공 결과를 함께
보존한다. 예기치 않은 프로세스 종료 뒤 실행 여부가 확인되지 않았다면 이를 성공이나
실패로 추정하지 않고, 중단·복구 대기 등의 상태와 마지막으로 확인한 정보를 표시한다.

취소나 일시 중단은 요청을 보냈다는 사실과 실제로 실행이 멈췄다는 결과를 구분한다.
이미 공개된 결과나 외부 제공자에 반영된 부작용이 자동으로 되돌아간다고 가정하지
않는다. 취소·일시 중단·재개·재시도 지원 여부는 작업별 능력으로 드러내고,
지원하지 않는 제어를 가능한 것처럼 표시하지 않는다.

진행률은 무엇을 얼마나 처리했는지와 단위가 분명해야 한다. 전체량을 모르면
불확정 진행으로 표시하며 임의의 비율이나 남은 시간을 만들지 않는다. 바이트 전송이
100%여도 대상 검증이나 결과 게시가 남아 있으면 해당 단계가 계속 진행 중임을
표시한다. 여러 단계를 하나의 비율로 합치는 경우 실제로 정의된 범위와 계산 기준에
근거해야 하며, 그 비율만으로 성공·판본 확정·보존을 주장하지 않는다.

성공은 작업 종류가 약속한 결과를 실제로 확인했을 때만 기록한다. 부분 성공,
이미 만들어진 산출물, 재시도가 필요한 단계는 숨기지 않는다. UI는 작업의 상태를
보여 주지만, 프리뷰 존재·로컬 저장·공유 판본 확정·원격 사본 검증과 같은 서로
다른 사실을 하나의 성공 배지로 합치지 않는다.

## 실행 수명과 복구

작업의 실행 소유자는 뷰보다 오래 사는 서비스 또는 플랫폼이 허용한 실행 주체가
된다. 화면을 닫거나 다시 만들어도 소유권은 유지하며, 실행 소유자가 제공하는 현재
상태에 다시 연결한다. 사용자가 명시적으로 취소하거나 권한 철회 등 작업 계약의
별도 중단 조건이 생긴 경우에는 그 요청과 실제 처리 결과를 따로 표시한다.

UI와의 독립성은 **앱 종료 후에도 무조건 실행된다**는 의미가 아니다. 작업 종류와
플랫폼에 따라 앱 종료 시 안전하게 중단, 데몬에 인계, 상태 보존 후 다음 실행에서
재개 또는 OS가 허용하는 백그라운드 실행을 선택할 수 있다. 실제 지원되는 정책과
조건을 사용자에게 구분해 보여 준다. 특히 모바일의 실행 시간과 재개는 OS 허가와
제한을 따른다. 앱을 닫았다는 이유만으로 완료를 표시하거나 OS가 중단한 작업을
계속 실행 중이라고 주장하지 않는다.

오래 걸리고 재개가 필요한 작업은 요청과 기준, 진행·검증 지점, 실패 또는 완료
결과를 복구 가능한 형태로 관리한다. 프로세스가 중단되면 마지막으로 안전하게 확인한
지점부터 재검증하거나 다시 시작한다. 원본·기존 사본·확정 판본을 보존하고, 검증이
끝나지 않은 부분 산출물을 완성된 결과로 게시하지 않는다. 짧거나 재생성 가능한
작업은 작업별 정책에 따라 중단 후 다시 생성할 수 있지만, 그 경우도 화면을 닫은
것과 작업을 취소한 것은 구분한다.

항목별 작업의 요청·각 항목 결과·집계·체크포인트·시도 관계는 앱을 종료하고 다시
열어도 조회할 수 있도록 영속 보관한다. 실행을 다시 시작하더라도 기존 완료 결과나
작업 기록을 지우지 않는다. 재시작 후 작업이 계속 실행되었다고 가정하지
않고, 실행 소유자와 마지막으로 확인한 상태를 다시 확인한다. 체크포인트는 대상과
기준 판본, 해당 시도에 연결하고 재개 전에 유효성을 검사한다. 중단 시 실제 결과를
확인하지 못한 항목은 성공 또는 실패로 임의 판정하지 않고 확인이 필요한 상태로 남긴다.

예를 들어 1,000개를 가져온 뒤 963개가 성공하고 37개가 실패했다면, 사용자는
**963개 성공·37개 실패**와 각 실패의 이유를 볼 수 있어야 한다. 앱을 다시 열어도
작업 ID, 항목별 결과와 산출물을 확인한다. 실패 항목 재시도는 그 37개 중 재시도가
가능한 실패 항목만 대상으로 하며, 성공한 963개를 다시 가져오거나 덮어쓰지 않는다.
재시도할 수 없는 항목과 외부 처리 결과가 불명확한 항목은 이유와 별도 확인 필요
상태로 남긴다. 재시도 과정의 결과와 횟수는 원래 요청에 연결하고 이전 시도 내역을
보존한다.

같은 요청의 재시도나 실행 소유자 인계는 중복 게시·중복 가져오기·기존 결과 덮어쓰기를
일으키지 않아야 한다. 동일 입력의 재시도와 다른 입력으로 시작한 새 작업을 구분하고,
응답이 사라졌을 때에는 현재 결과를 확인한 뒤 재시도한다. 외부 제공자가 결과 조회나
중복 방지 수단을 제공하지 않아 처리 여부를 알 수 없으면 불명확한 상태를 표시하고
무조건 다시 게시하지 않는다. 작업이 사용하는 대상 판본이 실행 중 바뀌면 기존 작업의
입력을 조용히 바꾸지 않고, 명시된 판본을 계속 처리하거나 안전하게 중단해 새 작업으로
전환한다.

## 판본 이벤트와 후속 작업

공유 내용 판본이 확정되면 그 사실에 따른 미리보기 생성, 색인 갱신, 알림 등의 후속
작업을 요청할 수 있다. 각 작업은 공통 Job 계약을 사용하며, 이벤트와 작업은 적어도
저장 공간, 자원 ID, 확정 판본 ID, 발생 원인과 처리 대상을 구분할 수 있어야 한다.
전문 앱의 로컬 저장이나 미확정 작업 사본 변경을 공유 판본의 확정 이벤트로 가장하지
않는다. 판본 확정만으로 사용자의 별도 게시 요청이 없는 게시물을 자동 생성하지 않는다.

### 이벤트 중복과 안전한 재처리

같은 이벤트를 다시 수신해도 같은 논리적 후속 작업이나 게시물이 중복 생성되지 않아야
한다. 이벤트 식별자와 처리 대상별 기록을 유지하고, 같은 사건에 서로 다른 전달
식별자가 붙는 경우에도 자원·판본·작업 종류와 실제 요청 의도에 근거해 중복 효과를
방지한다. 미리보기 크기·생성 조건, 알림의 수신자·채널 등 결과의 의미를 바꾸는
인자는 서로 다른 처리로 구분한다. 판본과 내용 해시가 같다는 사실만으로 서로 다른
자원이나 사용자가 의도한 별도 요청을 하나로 합치지 않는다.

판본 확정이 성공한 뒤 프로세스가 종료되어도 필요한 후속 처리가 조용히 누락되어서는
안 된다. 확정 기록과 함께 재처리 가능한 이벤트 또는 작업 요청을 안전하게 남기거나,
이미 확정된 기록에서 누락된 후속 처리를 복원할 수 있는 동등한 수단을 사용한다.
일회성 메모리 신호나 화면 알림만을 유일한 전달 근거로 사용하지 않는다.

가능한 곳에서는 중복 검사·작업 접수·처리 기록을 같은 트랜잭션 경계에서 다룬다.
파일 게시나 외부 서비스 호출처럼 하나의 트랜잭션으로 묶을 수 없는 효과는 임시
결과와 복구 가능한 처리 기록, 대상의 중복 방지 키 또는 결과 재조회로 조정한다.
처리 성공 후 확인 응답이 유실되어도 이미 만들어진 결과를 다시 확인하고 중복 게시나
중복 알림을 피한다. 대상이 중복 방지나 결과 조회를 지원하지 않아 실제 처리 여부를
알 수 없다면 **결과 확인 필요**로 남기며, 확실한 한 번의 처리를 보장한다고 주장하거나
무조건 재발송하지 않는다.

중복 방지 기록의 보존·정리 정책도 재전달과 복구 범위에 맞춰야 한다. 오래된 전달의
재시도 때문에 이미 게시한 효과가 다시 만들어지지 않아야 하며, 재처리와 별도로
사용자가 새로 요청한 의도적인 재생성은 구분한다.

### 늦게 도착한 판본과 결과 게시

미리보기와 색인 작업은 자신이 입력으로 받은 정확한 판본과 생성 조건을 기록한다.
최신 상태를 보여 주는 결과를 게시할 때에는 그 판본이 해당 자원의 현재 확정 판본인지
최종 게시 시점에 다시 확인한다. 계산 중 최신 판본이 바뀌었거나 오래된 이벤트가
나중에 도착했으면 이전 결과로 최신 미리보기·색인을 덮어쓰지 않는다. 결과 저장소는
게시된 판본의 순서 또는 동등한 세대를 조건부로 비교·갱신하여 이미 게시한 더 새로운
결과가 뒤로 돌아가지 않게 한다. 삭제된 자원의 기록도 유지해 늦은 이전 결과가 삭제된
항목을 최신 색인에 다시 나타나게 하지 않는다.

판본을 확정하는 저장소와 색인 저장소가 다르면 둘 사이에 하나의 원자적 트랜잭션이
있다고 가정하지 않는다. 새 판본이 확정되었지만 색인이 아직 갱신되지 않은 동안에는
색인된 판본과 마지막으로 확인한 확정 판본을 구분해 **색인 갱신 대기 또는 미확인**으로
표시하고 후속 처리를 복구한다. 조건 비교에 쓰는 순서·세대를 검증할 수 없으면 최신
결과를 덮어쓰지 않는다.

판본 순서는 해당 저장 공간의 확정 주체가 제공하는 판본 관계나 순서에 근거한다.
기기 시계, 파일 수정 시각, 해시의 사전식 순서로 최신 판본을 결정하지 않는다. 확정
주체나 이력을 확인할 수 없다면 최신 여부는 미확인으로 두고 재조정한다. 특정 과거
판본에 고정된 게시물이나 이력을 위한 결과는 그 판본에 연결하여 보존할 수 있지만,
현재 판본의 결과로 표시하지 않는다.

같은 판본에 대해 사용자가 미리보기를 다시 생성하거나 생성 조건을 바꾼 경우에도
요청과 결과를 구분한다. 이전 생성 작업이 늦게 끝나 더 나중에 승인된 생성 요청의
결과를 덮어쓰지 않도록, 대상 판본뿐 아니라 해당 결과의 최신 요청 또는 세대도 게시
시 확인한다. 요청 순서를 사용자 기기의 시각만으로 판단하지 않는다. 더 이상 최신
결과 게시에 유효하지 않은 작업은 대체되었음을 기록하며 성공한 최신 결과로
오인시키지 않는다.

### 실패 표시와 재시도

후속 작업의 실패·대기·취소·재시도 결과는 작업과 해당 자원에 연결해 남긴다. 일시적
오류의 자동 재시도는 작업 종류별 제한과 대기 정책을 따르며, 재시도 한도 소진이나
권한·지원 형식 등 자동으로 해결할 수 없는 오류는 조용히 버리지 않는다. 화면을
닫거나 프로세스를 다시 시작해도 판본 확정에 따른 미해결 실패를 다시 확인할 수 있어야
한다. 해결·사용자 확인 이후 기록을 정리하는 경우에도 그 보존 정책을 분명히 한다.

사용자는 해당 자원의 화면이나 인스펙터에서 예를 들어 **미리보기 생성 실패 → 다시
생성**을 선택할 수 있어야 한다. 상태에는 실패한 작업·대상 판본·실패 이유와 가능한
행동을 표시한다. 재시도는 원래 작업의 입력과 권한을 다시 확인한다. 대상 판본이
바뀌었다면 어떤 판본을 다시 처리할지 분명히 하고, 오래된 판본의 재처리를 현재
판본의 성공으로 표시하지 않는다. 같은 실패 작업의 재시도와 완료된 결과에 대한
사용자의 새로운 재생성 요청은 구분한다.

예를 들어 자원 `R`의 판본 `C1` 미리보기 생성이 실패하면 `R`에서 `C1`의 실패와
재시도를 확인한다. 그 사이 `C2`가 확정되어 미리보기와 색인이 갱신되었다면, 늦게
끝난 `C1` 작업이나 같은 `C1` 이벤트의 재전달은 `C2`의 최신 결과를 바꾸지 않는다.
사용자가 `C1`의 재생성을 별도로 요청하면 그 결과는 `C1`에만 연결된다.

초기 우선순위는 내부에서 정한 후속 작업의 생성·상태·실패·재시도 계약을 일관되게
만드는 것이다. 범용 워크플로 편집기나 사용자가 임의의 작업 그래프를 구성하는 기능은
이 단계의 필수 범위가 아니다.

## 관찰과 제어 경계

- Society의 작업 서비스가 작업 상태와 수명을 소유하고, 각 도메인 SDK는 실제
  전송·검사·색인·패키징 등의 책임을 유지한다. GUI는 관찰 및 명시적 제어를 위한
  표현 계층이다. 데몬 사용 여부는 작업과 플랫폼의 실행 조건에 따른다.
- 상태 조회·변경 구독과 작업 요청·취소·재시도는 명확한 인터페이스로 구분한다.
  UI와 에이전트는 동일한 작업 정체성과 권한 검사를 사용한다. 앱에는 CLI 또는
  이에 준하는 에이전틱 인터페이스를 제공하되, 지원 작업과 실제 권한 범위를 밝힌다.
- 비 GUI 계약은 Qt나 특정 화면에 종속되지 않아야 한다. 지속 워커·유한 대기열·
  협력적 취소·타입이 있는 조회 및 구독에 기존 iiSDKCore의 기능을 검토한다.
  Future나 상태 스트림 자체가 영속 작업 저장소·프로세스 간 인계·복구를 제공한다고
  가정하지 않는다.
- 대용량 데이터는 제한된 자원으로 처리하고, 실행 슬롯·대기열·저장 공간과
  동시성을 관리한다. 백그라운드 작업 때문에 UI가 동기적으로 대기하지 않도록 한다.
- 작업 로그와 에이전트 결과는 자격 증명이나 원본 내용을 불필요하게 포함하지 않는다.
  작업 생성·조회·제어와 결과 접근은 요청 주체와 자원에 적용되는 권한을 확인한다.

## 기존 구현과 이행 경계

- 모델 가져오기는 독립 C++23 모듈 iiJob의 영속 작업 ID, 항목별 결과, 체크포인트와
  시도 기록을 사용한다. 저장 파일과 실행 잠금은 Society가 iiFileProvider로 만들고,
  모델의 관리 객체 세션에는 작업 ID와 항목 ID를 기록한다. 모델 화면의 가져오기
  이력에서 항목 결과를 조회하고 실패한 항목을 재시도할 수 있다. 현재는 모델
  가져오기 한 경로에 적용되며 다른 작업 유형에 자동 적용되지는 않는다.
  [모델 문서](Models.md), [iiJob 계약](../../../SDK/iiJob/docs/Jobs.md)
- Projects는 작업 스레드에서 목록·수정·파일 복사를 수행하며, 현재 화면은 앱 종료
  또는 컨테이너 전환 중 진행 중인 복사의 취소 기능을 제공하지 않는다.
  [Projects 문서](Projects.md)
- 현재 Sync와 SocietyDaemon은 동기화 수명·소유권 인계 및 일부 상태를 다룬다.
  썸네일·가져오기·패키징·배포까지 포괄하는 공통 작업 서비스로 취급하지 않는다.
  [동기화 문서](Synchronization.md), [데몬 문서](SocietyDaemon.md)
- 데몬 수신함은 동일 메시지 ID의 중복 저장을 방지하고, iiFileProvider Catalog는
  일부 메타데이터 게시 실패를 저널에 남겨 재시도한다. 이 개별 계약이 이 문서의
  판본 확정 이벤트 전체, 외부 효과의 중복 방지 또는 최신 색인 게시 조건까지 이미
  보장하는 것은 아니다. [데몬 문서](SocietyDaemon.md),
  [Catalog 복구 경계](../../../SDK/iiFileProvider/docs/FILE_CATALOG.md#recovery-and-boundaries)
- 현재 Society MCP는 상태와 탐색 등 제한된 도구를 제공한다. 공통 작업의 생성·조회·
  취소·재시도 API가 이미 제공된다는 뜻은 아니다. [MCP 문서](Mcp.md)
- iiSDKCore의 Runtime, Concurrent와 QueryStream은 유한 실행·진행 관찰·협력적
  취소·타입 있는 구독을 구성하는 기반이다. 작업의 제품별 권한·영속성·복구·
  전송 검증을 자동으로 수행하지 않는다.
  [Concurrent 계약](../../../SDK/iiSDKCore/docs/concurrent.md),
  [QueryStream 계약](../../../SDK/iiSDKCore/docs/query-stream.md)

기존 작업별 결과와 사용자 데이터를 보존하면서 공통 인터페이스에 단계적으로 연결한다.
실제 지원 범위는 각 기능·플랫폼의 구현과 검증 결과를 기준으로 표시한다.

### 모델 가져오기의 저장과 복구 경계

작업 기록은 Society의 앱별 로컬 데이터 디렉터리의 `jobs/`에 SQLite와 그 WAL로
보관한다. 앱 재시작 뒤에는 모델 화면의 가져오기 이력에서 최근 100개 작업과 각
작업의 항목을 100개씩 조회할 수 있다. 개별 항목에는 오류, 성공 경로, 시도 횟수와
마지막 체크포인트가 남는다. 실행 중 프로세스가 사라졌는지 확인할 때는 해당 Job의
배타 잠금을 획득한 뒤에만 복구한다. 결과를 알 수 없는 항목은 **확인 필요**로 남고
자동으로 실패나 재시도 대상으로 바뀌지 않는다. 반대로 모든 항목의 결과가 이미
확정되고 마지막 작업 종료 기록만 누락된 경우에는 기존 결과를 바탕으로 작업을
마무리한다.

Society를 빌드하기 전에 대상 플랫폼용 iiJob 패키지를 설치하거나 CMake의 `iiJob_DIR`에
그 패키지의 설정 디렉터리를 지정한다. SQLite는 iiJob의 외부 의존성이며 Society가
iiJob과 iiFileProvider를 조합한다. iiJob이 iiFileProvider에 직접 의존하지는 않는다.

앱 내부의 `ModelImporter`는 `jobs`, `selectedJobId`, `jobItems`,
`hasMoreJobItems`, `jobsError`를 노출한다. `refreshJobs()`와 `selectJob(id)`는
백그라운드에서 현재 기록을 다시 읽고 `jobsChanged`를 알린다. 항목은
`loadMoreJobItems()`로 이어서 조회한다. `retryFailed(id)`의 반환값은 비동기 실행을
접수했는지이며 성공 판정이 아니다. 결과는 `finished`와 갱신된 Job·항목 상태로
확인한다. 이전 시도 각각은 iiJob의 `Store::history()`에서 조회할 수 있다.

로컬 원본의 실패는 명시적인 재시도에서만 다시 읽는다. 이미 성공한 항목은 다시
복사하지 않는다. 파일이 게시된 뒤 관리 색인 등록에 실패하거나 취소되면 저장된
경로와 SHA-256 체크포인트를 검증하고 등록부터 다시 시도한다. 검증에 실패하면
새 파일을 만들지 않고 해당 항목의 확인이 필요하다. 게시와 체크포인트 기록 사이에
중단될 수도 있으므로 그때의 결과는 자동 추측하지 않는다. 복사 중 체크포인트의
바이트 수는 관찰 정보이며 임시 파일의 바이트 이어쓰기 보장은 아니다. 이미 복사를
시작했던 로컬 원본의 재시도는 경로·크기·수정 시각을 대조하고 달라졌다면 새
가져오기를 요구한다. 이 대조는 내용 해시나 확정된 내용 판본의 증명이 아니며,
같은 메타데이터를 유지하며 바뀐 내용까지 판별하지는 못한다.

일시적인 Apple 제공자 접근권이나 Android content URI를 장기 권한으로 가정하지
않는다. 게시 전에 실패한 그런 항목은 다시 선택해야 한다. 앱이 종료된 동안 OS가
작업을 계속 실행하거나 다른 기기로 작업을 이관한다는 보장은 없다. 작업 생성 전
드라이브 자체를 열 수 없는 요청은 현재 작업 DB에 접수되지 않는다. 현재 작업의
접근 제어는 로컬 앱의 데이터 권한에 한정되며, 별도 주체별 인가 및 원격 MCP 작업
제어는 후속 범위다.

## 구현 시 수용 검증

1. 업로드, 가져오기 또는 패키징을 시작하고 화면을 이동·제거·재생성해도 작업 ID와
   상태를 다시 조회할 수 있으며, 화면 종료만으로 작업이 취소되지 않는다.
2. 두 관찰자가 같은 작업을 구독할 때 한쪽이 닫혀도 다른 쪽과 작업이 유지된다.
   누락된 알림 뒤에는 현재 상태 조회로 복구한다.
3. 전송 100% 뒤 검증이 남은 작업은 성공이 아니며, 검증 실패는 해당 단계와 대상
   판본을 표시한다. 전체량을 모르는 작업은 허위 진행률을 만들지 않는다.
4. 취소 요청이 처리되기 전에는 취소 완료를 표시하지 않고, 이미 게시된 결과와
   부분 산출물의 상태를 실제 결과에 맞게 기록한다.
5. 실패·응답 유실·재시작 뒤 재시도에서 원본과 기존 결과를 보존하고 동일 요청의
   중복 확정이나 중복 게시를 방지한다.
6. 앱 종료, 실행 소유자 인계, 기기 재시작, 모바일 백그라운드 제한에서 각 작업의
   명시된 수명 정책에 맞게 중단·복구·재개 상태를 표시한다.
7. 처리 도중 입력 판본이 바뀌어도 진행 중인 작업은 지정 판본의 결과로 남고, 새
   편집을 잘못 완료 또는 보존 완료로 표시하지 않는다.
8. 여러 작업과 대기 중인 관찰자가 있어도 실행·대기·알림 자원은 제한되며, UI 조회는
   장시간 디스크·네트워크 작업을 동기적으로 기다리지 않는다.
9. 권한이 없는 UI 또는 에이전트는 다른 주체의 작업과 민감한 결과를 조회하거나
   제어하지 못한다. 로그와 오류에 자격 증명을 남기지 않는다.
10. 같은 확정 이벤트의 중복 전달과 서로 다른 전달 ID를 가진 같은 논리 요청이 와도
    후속 작업·게시물·알림 효과가 중복되지 않는다. 서로 다른 수신자·생성 조건 또는
    사용자의 별도 재생성 의도는 잘못 합쳐지지 않는다.
11. 판본 확정 직후나 후속 작업 접수·결과 게시·확인 응답의 각 경계에서 중단하고
    재시작해도 필요한 작업을 복구하며, 이미 게시한 결과를 중복 생성하지 않는다.
12. 이전 판본 이벤트가 최신 판본 처리 이후 도착하거나 오래된 작업이 나중에 끝나도
    현재 미리보기와 색인을 되돌리지 않는다. 명시된 과거 판본 결과는 구분해 조회할
    수 있다. 삭제 후 도착한 오래된 이벤트는 항목을 최신 색인에 되살리지 않는다.
13. 같은 판본의 연속 재생성 요청이 역순으로 끝나도 먼저 요청한 작업이 나중 요청의
    결과를 덮어쓰지 않는다. 판본 순서는 기기 시계에 의존하지 않는다.
14. 미리보기·색인·알림의 실패와 자동 재시도 한도 소진을 자원과 작업에 표시하고,
    사용자가 자원에서 대상 판본을 확인한 뒤 실패 작업을 다시 실행할 수 있다.
15. 외부 서비스의 처리 결과가 불명확하고 중복 방지·조회가 불가능할 때에는 성공이나
    실패를 추측해 재발송하지 않고 확인이 필요한 상태를 보존한다.
16. 1,000개 가져오기에서 963개 성공·37개 실패가 발생하면 앱을 재시작해도 같은 작업의
    항목별 결과·오류·산출물과 집계를 조회할 수 있다.
17. 실패 항목만 재시도하면 성공한 963개는 재처리하거나 덮어쓰지 않는다. 각 실패의
    재시도 가능 여부와 모든 시도 내역은 유지하고 집계는 항목을 중복 계산하지 않는다.
18. 노드 대기와 권한 대기에서 필요한 기기 또는 접근 행위와 대상을 구분해 보여 준다.
    대상을 알 수 없다면 추측하지 않는다.
19. 부분 결과가 생긴 뒤 취소하면 실제 중단과 이미 성공·게시된 항목을 함께 표시한다.
    요청 중인 취소를 완료된 취소로 표시하지 않는다.
20. 재시작 후 체크포인트와 기준 판본을 재확인하며, 외부 처리 결과가 불명확한 항목을
    실패로 추정해 무조건 재전송하지 않는다.
