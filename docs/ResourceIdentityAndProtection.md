# Society 자원 정체성, 판본 및 보존 상태 명세

## 목적과 적용 상태

이 문서는 여러 앱과 기기에서 창작 자원을 다루기 위한 **목표 제품 계약**이다.
여기에 적힌 객체, 상태와 화면 요구사항은 구현 완료를 주장하지 않는다. 현재 구현과
이 명세의 차이는 [기존 구현과 이행 경계](#기존-구현과-이행-경계)에 따로 기록한다.
구현 시에는 기존 데이터와 오프라인 작업을 보존하고 각 SDK의 책임을 유지해야 한다.

가장 먼저 자원의 ID, 표시 경로, 내용 판본, 실제 저장 위치를 분리한다. Society는
사용자가 자원을 선택했을 때 **어디에 있는가, 지금 열 수 있는가, 최신인가, 다른
곳에도 보존되었는가**에 각각 근거를 제시해야 한다.

## 객체와 책임

Resource, Content Revision, Location과 Replica의 공용 타입 및 Society의 현재
저장소 어댑터는 [iiResource 연결 문서](ResourceModule.md)를 따른다. 기존 데이터
이전이나 모든 저장소 간 ID 통합이 완료되었다는 뜻은 아니다.

- 객체: Asset / Resource; 의미: 파일·모델·창작 에셋의 논리적 정체성. 이름·경로·기기와 독립된 `resource_id`를 갖는다.; 분리해야 하는 것: 이름, 표시 경로, 기기, 내용 해시
- 객체: Working copy; 의미: 전문 앱이 현재 읽고 수정하는 로컬 작업 사본; 분리해야 하는 것: 확정된 내용 판본과 편집의 기준 판본
- 객체: Content revision; 의미: 자원 내용의 일관되게 확정된 불변 판본. 기준 판본과 내용 검증값을 기록한다.; 분리해야 하는 것: 작업 중인 바이트, 메타데이터 변경
- 객체: Metadata revision; 의미: 설명·태그·분류·스키마 값 등의 변경 이력; 분리해야 하는 것: 파일 내용 판본
- 객체: Location / Replica; 의미: 실제 저장 위치와 그곳에 놓인 특정 판본의 사본; 분리해야 하는 것: 자원 자체와 다른 위치의 사본
- 객체: Project; 의미: 사용자가 명시한 목표와 이를 위한 자원·엔터티·관계; 분리해야 하는 것: 저장 폴더, 소유권, 참여자 목록과 구성 자원 목록
- 객체: Release; 의미: 배포할 특정 판본들의 확정된 묶음; 분리해야 하는 것: 작업 중인 최신 상태와 게시물
- 객체: Publication; 의미: 설명·프리뷰·공개 범위 등을 가진 게시물; 분리해야 하는 것: 내부 자원, 릴리스, 접근 권한
- 객체: Grant / Entitlement; 의미: 특정 주체의 접근·이용 범위와 그 부여 근거; 분리해야 하는 것: 자원·사본의 존재, 프로젝트 참여
- 객체: [Job](JobsAndOperations.md); 의미: 요청·단계·실행자·결과를 가진 작업; 분리해야 하는 것: 개별 UI 화면과 그 수명
- 객체: [Node](DeviceStateAndCapabilities.md); 의미: 저장소나 연결된 기능을 제공하는 사용자 기기; 분리해야 하는 것: 연결 여부, 기능별 상태와 각 관찰 시각

자원·내용 판본·메타데이터 판본·저장 위치·프로젝트·릴리스·게시물·권한·작업·Node는
각각 별도의 식별 및 수명을 가진다. 식별자의 생성 주체와 범위는 구현 계약에서
정하며, 이름이나 물리 경로를 식별자로 재해석하지 않는다.

이 객체들이 각각 최상위 메뉴가 될 필요는 없다. 자원 검색은 뷰와 필터로 접근하며,
검색 색인은 정본의 변경과 독립적으로 비동기 갱신한다. 뷰·필터·색인과 이 객체들의
관계, 최신성·불완전 결과의 표시는 [자원 검색과 뷰 계약](ResourceSearchAndViews.md)을
따른다.

### 먼저 분리할 네 가지 값

- 값: 자원 ID; 의미와 변경 경계: 논리적 자원의 식별자이다. 확인된 이름 변경·이동이나 사본 추가로 바뀌지 않는다.
- 값: 표시 경로; 의미와 변경 경계: 사용자가 자원을 찾고 이해하기 위한 이름과 경로이다. 자원 ID나 어느 기기의 실제 접근 경로를 대신하지 않는다.
- 값: 내용 판본 ID; 의미와 변경 경계: 특정하게 확정된 내용의 판본을 식별한다. 메타데이터만 바뀌거나 같은 판본이 다른 곳에 놓인 사실만으로 새 내용 판본을 만들지 않는다.
- 값: 실제 저장 위치; 의미와 변경 경계: 기기 또는 제공자와 실제 locator 및 그곳에서 확인된 판본을 나타낸다. 한 자원에 여러 위치가 있을 수 있다.

자원 참조는 자원 ID를, 판본에 고정된 참조는 자원 ID와 내용 판본 ID를 사용한다.
위치가 알려져 있다는 것만으로 그 판본이 현재 존재하거나 접근·검증되었다고
판단하지 않는다. 이름·경로·내용 해시가 같다는 이유로 별도 자원을 합치지 않는다.

### 자원과 판본

> 자원의 이름이나 저장 위치를 변경해도 자원 ID와 프로젝트 참조는 유지된다.
> 내용 변경은 새로운 내용 판본을 생성하며, 복제는 같은 자원의 특정 판본을 다른
> 위치에 배치한다.

여기서 내용 판본의 생성은 임의의 키 입력마다가 아니라 저장된 작업 사본에서
Society가 **일관된 내용을 확정하는 시점**을 뜻한다. 작업 사본에는 어느 자원과
어느 확정 판본을 기준으로 편집하는지 기록한다. 아직 확정되지 않은 새 작업에는
기준 판본이 없음을 명시한다. 여러 작업 사본과 그 기준이 다를 수 있으며, 한
사본의 완료가 다른 사본의 변경을 없애지 않는다.

내용 해시는 특정 바이트의 동일성 확인과 무결성 검증에 사용한다. 자원 ID도 내용
판본 ID도 해시와 같은 뜻이 아니다. 내용이 같은 서로 다른 자원은 서로 다른
소유권·이용 조건·사용 맥락을 가질 수 있다. 동일한 바이트가 서로 다른 시점이나
계보의 판본에 등장할 수도 있다. 해시가 같다는 이유만으로 자원·권한·프로젝트
관계를 자동 병합하지 않는다. 내부 바이트 중복 제거는 이 논리적 구분을 보존해야
한다. 사용자가 입력한 해시와 실제 바이트를 검증한 해시는 구분한다.

자원 이름 변경, 확인된 이동과 재배치는 ID를 유지하고 해당 표시 경로 또는 위치를
갱신한다. 단순히 이름·경로·해시가 비슷하다는 것만으로 서로 다른 자원을 같은
자원으로 합치지 않는다. 사본 배치는 기존 자원과 **정확한 내용 판본**을 참조한다.
사용자가 독립된 자원 생성이나 포크를 선택한 경우에는 새 정체성과 필요한 출처
관계를 기록한다.

- 변경: 이름 또는 표시 경로 변경; 자원 ID: 유지; 내용 판본: 바이트가 같으면 유지; 저장 위치와 사본: 실제 경로가 달라졌다면 해당 위치를 갱신한다.
- 변경: 작업 사본의 내용 변경과 확정; 자원 ID: 유지; 내용 판본: 일관된 내용을 확정할 때 새 판본을 만든다.; 저장 위치와 사본: 각 위치가 실제 보유·검증한 판본은 따로 기록한다.
- 변경: 확인된 저장소 이동; 자원 ID: 유지; 내용 판본: 같은 확정 내용을 옮긴다면 유지; 저장 위치와 사본: 사본의 기존·대상 위치와 각 관찰·검증 상태를 갱신한다.
- 변경: 독립 자원 생성 또는 포크; 자원 ID: 새 ID; 내용 판본: 적용되는 판본과 출처 관계를 기록한다.; 저장 위치와 사본: 새 자원의 실제 위치를 기록한다.

저장소 이동이 복사 후 원본 제거로 이루어지더라도 완료를 한 번에 가정하지 않는다.
대상에 해당 판본이 게시·검증됐는지와 기존 사본이 실제로 제거됐는지를 각각
기록한다. 이동이나 이름 변경만으로 다른 사본의 보유·검증 상태를 바꾸지 않는다.

### Society를 거치지 않은 파일 이동

Finder나 다른 앱 등 Society 외부에서 파일이 이동되면 파일시스템이 제공하는 볼륨과
파일 식별 정보, 관찰된 변경 이력, 신뢰할 수 있는 이동 기록 등 **확인 가능한
연속성**을 조사해 기존 자원 및 사본과 연결한다. 파일시스템 식별 정보는 그
파일시스템과 관찰된 수명 안에서 사용할 근거이며, `resource_id` 자체는 아니다.
각 판단에 사용한 근거와 관찰 시점을 남기고, 접근할 수 없는 경로를 실제 부재로
단정하지 않는다.

식별자의 재사용이나 저장소 교체, 다른 볼륨으로의 복사 후 삭제, 하드 링크,
원본 교체, 여러 후보, 누락된 관찰 또는 부분 스캔 등으로 연속성을 확인할 수
없으면 관계를 미확인으로 둔다. 파일명·경로·크기·시간·내용 해시의 일치나 이전
경로의 부재만으로 동일 자원이라고 확정하지 않는다. 해시는 내용과 무결성을
검증하는 데 쓸 수 있지만 소유권·라이선스·사용 맥락의 동일성을 증명하지 않는다.
판정이 모호할 때는 기존 자원·판본·프로젝트 참조와 발견된 파일을 보존하고,
임의로 병합하거나 이력을 덮어쓰지 않는다. 나중에 충분한 근거가 확보되거나
사용자가 확인한 관계를 안전하게 반영할 수 있어야 한다.

설명·태그·스키마 값 등의 메타데이터 변경은 메타데이터 판본을 갱신한다. 내용이
바뀌지 않았다면 별도의 내용 판본이나 원본 재전송을 만들었다고 표시하지 않는다.
내용과 메타데이터가 함께 바뀌면 각 변경을 별도로 기록하고 같은 작업 맥락으로
연결할 수 있다. 한 판본의 기록이 존재한다는 사실은 과거 바이트가 어느 위치에
보존되어 있다는 보장이 아니다. 유형별 의미, 속성·관계의 출처와 검증 상태는
[에셋 의미와 출처 명세](AssetSemanticsAndProvenance.md)를 따른다.

### 참조와 위치

- 자원에 대한 참조는 자원 ID를 기본으로 삼는다. 프로젝트는 자원을 직접 소유하거나
  프로젝트 폴더에 복사해야만 참조할 수 있는 것이 아니다.
- 참조가 최신 확정 판본을 따르는지, 특정 내용 판본에 고정되는지 명시한다. 최신을
  따르는 참조와 고정 참조의 기준은 서로 바꾸어 해석하지 않는다.
- 릴리스는 구성 자원과 정확한 내용 판본을 확정해 기록한다. 공개된 게시물의 실제
  콘텐츠와 프리뷰도 표시하는 판본에 연결하며, 원본의 최신 내용으로 자동 대체하지
  않는다. 새 판본 게시·교체는 별도 행위이다.
- 위치와 사본은 자원 ID, 내용 판본 ID, 기기 또는 제공자, 실제 locator 및 관찰
  상태를 연결한다. 표시 경로는 사용자를 위한 표현이고 실제 접근 경로나 각
  기기에서 사용할 locator와 같다는 보장은 없다.
- 한 자원은 여러 프로젝트와 게시물에서 참조할 수 있고, 한 판본은 여러 위치에
  놓일 수 있다. 권한이나 프로젝트 참여만으로 원본 바이트가 그 위치에 존재하거나
  현재 사용자에게 열기 권한이 있다고 판단하지 않는다.

## 권한은 대상에 대한 행위로 정의한다

권한은 **누가, 어떤 대상에, 어떤 행위를, 어떤 범위와 조건에서 할 수 있는지**로
표현한다. 대상의 정체성과 필요한 경우 판본·프로젝트·저장 위치의 범위를 명시한다.
주체는 사용자뿐 아니라 명시적으로 위임받은 앱·서비스·에이전트일 수 있으며,
요청 주체와 위임 근거를 구분한다. 인증된 계정이라는 사실, 파일의 존재, 프로젝트
참여 또는 같은 내용 해시는 그 자체로 별도의 행위 권한을 만들지 않는다.

- 대상: 에셋; 독립적으로 판단할 행위: 메타데이터 보기, 미리보기 보기, 원본 읽기, 새 내용 판본 쓰기, 삭제, 복원
- 대상: 프로젝트; 독립적으로 판단할 행위: 목표 읽기, 목표 수정, 구성 자원 읽기, 구성 자원 수정, 공유 범위 관리
- 대상: 게시물; 독립적으로 판단할 행위: 초안 수정, 공개, 공개 중단
- 대상: 저장 위치; 독립적으로 판단할 행위: 목록 조회, 읽기, 쓰기, 전송, 저장 정책 변경
- 대상: 공유·위임; 독립적으로 판단할 행위: 권한 부여, 권한 축소, 만료 변경, 철회

사용자에게는 소유자·편집자·열람자 같은 역할을 보여 줄 수 있다. 내부에서 역할은
이러한 개별 행위의 묶음으로 정의하고, 역할에 포함된 행위와 적용 범위·기간을
확인할 수 있어야 한다. 역할 이름만으로 모든 대상에서 동일한 권한이 자동으로
생긴다고 가정하지 않으며, 실제 판단은 그 대상에 적용되는 유효한 부여와 조건을
기준으로 한다. 여러 대상이 관여하는 작업은 각 대상에 필요한 행위를 따로 판단한다.

특히 다음 권한은 서로를 대신하지 않는다.

- 메타데이터·미리보기 열람과 원본 읽기 또는 다운로드
- 내용 편집·새 판본 쓰기와 공유 범위 또는 권한 변경
- 결과 생성·내부 저장과 게시물의 외부 공개
- 복제본의 존재·목록 조회와 해당 판본의 읽기·전송
- 권한 부여, 기존 권한의 축소·만료 변경·철회

Grant / Entitlement는 적용 대상과 주체, 허용 행위, 유효 범위·기간 및 공유·구매
등의 부여 근거를 구분해 기록한다. 구매나 공유는 권한의 근거가 될 수 있지만,
어떤 대상의 어떤 행위가 부여되었는지는 별도로 확인한다. 만료·철회되었거나 유효성을
확인할 수 없는 부여를 유효한 접근 권한으로 취급하지 않는다. 대기·재시도 중인 작업도
실제 수행과 외부 공개 시점에 필요한 행위 권한을 확인한다.

현재 iiSocietyContainer가 저장하는 Entitlement JSON과 그 무결성 정보는 이 권한 모델의
저장 기반이다. JSON이 존재하거나 형식이 유효하다는 것만으로 부여의 진위 검증,
행위별 접근 판정, 철회 전파 또는 서버·OS 차원의 집행이 구현된 것은 아니다.
기존 계정·제품 라이선스 확인과 자원별 접근 판정도 서로 구분한다.

## 기준 판본을 포함한 변경 제출

공유 자원의 내용 변경을 제출할 때에는 자원 ID, 편집의 **기준 내용 판본 ID**,
제출할 일관된 작업 내용과 제출 식별자를 함께 전달한다. 기준 판본은 편집을 시작한
시점의 확정 판본이며 제출 직전에 관찰한 최신 판본으로 조용히 바꿀 수 없다.
아직 기준 판본이 없는 새 자원은 그 사실을 명시하여 생성으로 제출하고, 이미 같은
정체성이 있는 자원을 덮어쓰지 않는다.

해당 저장 공간의 확정 주체는 제출을 적용하는 시점의 현재 확정 판본과 기준
판본을 비교한다. 둘이 일치하고 제출 내용이 일관되면 새 내용 판본을 확정할 수
있다. 다르면 어느 쪽도 무통보로 덮어쓰지 않고 **충돌**로 기록·보존한다. 비교와
확정은 경쟁 변경이 끼어들지 않도록 처리하며, 전송을 시작할 때 기준이 일치했더라도
실제 적용 전에 다시 달라졌으면 충돌로 처리한다.

제출 내용은 확정 주체가 그 내용을 안전하게 보관했다는 확인을 받기 전까지 제출
기기에 남겨 둔다. 전송 중단·재시작·확인 응답 유실 후에는 같은 제출을 안전하게
재시도하고, 한 번 확정한 제출을 중복 판본이나 중복 충돌로 만들지 않아야 한다.
보존에 필요한 저장 공간이나 검증이 부족하면 기존 확정 내용과 제출 내용을 그대로
두고 실패 또는 재시도 상태를 알린다.

### 충돌과 해결

이미지·영상·모델 등 바이너리 내용은 **양쪽 판본을 보존하는 것**이 기본이다.
충돌 기록은 자원, 공통 기준 판본, 현재 확정 판본, 제출된 내용과 확인 가능한
작성 기기·시각·처리 상태를 연결한다. 시각·파일명·해시만으로 승자를 정하거나
한쪽을 폐기하지 않는다. 제출 내용이 아직 확정 판본이 아니라면 그 사실도 표시한다.
삭제와 내용 수정이 경합할 때에도 수정된 바이트와 삭제 요청을 구분해 보존한다.

사용자는 충돌 항목과 각 내용을 확인하고 유지할 내용이나 두 내용의 보존을 선택할
수 있어야 한다. 해결을 새 확정으로 제출할 때에도 그 작업의 기준 판본을 확인한다.
그 사이 확정 판본이 다시 바뀌었다면 이전 선택을 강제로 적용하지 않고 다시 충돌을
알린다. 해결은 기존에 판본을 고정한 릴리스나 게시물을 자동으로 바꾸지 않는다.

자동 병합은 별도로 지원하는 포맷에 대해서만 제공한다. 지원 여부와 처리 정책을
사용자가 알 수 있어야 하며, 병합 입력과 결과를 구분하고 원래 양쪽 내용을
보존한다. 안전하게 병합할 수 없는 포맷이나 경우는 충돌로 남긴다. 내용 병합은
별도의 메타데이터 변경 이력과 혼동하지 않는다.

## 단일 확정 주체와 오프라인 작업

초기에는 **각 논리 저장 공간마다 하나의 주 노드**가 공유 내용 판본을 확정한다.
Mac, NAS 또는 Cloud에 사본을 두는 것과 확정 주체가 되는 것은 별개이다. 연결이
끊겼다는 이유만으로 다른 사본을 주 노드로 자동 승격하지 않는다. 확정 주체 변경이나
복구가 필요하면 기존 작업과 이력을 보존하는 별도의 절차가 필요하다.

주 노드에 연결할 수 없는 다른 기기에서도 전문 앱의 로컬 작업과 저장은 계속할 수
있다. 기준 판본, 제출 대기 내용 및 작업 상태는 기기 재시작과 재접속을 견딜 수
있도록 보존한다. 로컬 임시 스냅샷이나 로컬 저장 완료는 주 노드가 승인한 공유
판본으로 표시하지 않는다. 재접속하면 저장된 기준과 현재 확정 판본을 비교하여
일치하는 변경은 확정하고, 달라진 변경은 충돌로 보존한다.

주 노드 자체에서 작업할 때에는 다른 기기나 인터넷이 연결되지 않아도 주 노드의
확정 계약에 따라 판본을 확정할 수 있다. 이때에도 다른 기기의 수신·검증이나 전체
기기의 최신 상태 일치까지 완료되었다고 표시하지 않는다. 주 노드에 닿지 못하는
기기에서는 마지막으로 확인한 공유 판본과 시각을 보여 주되, 현재 공유 상태가
확정·동기화되었다고 단정하지 않는다.

## 세 가지 완료 경계

- 완료: 로컬 작업 사본 저장; 완료의 의미: 전문 앱이 해당 기기의 작업 사본 저장을 완료했다고 보고했다.; 이 완료만으로 보장하지 않는 것: Society 판본 확정, 다른 기기 접근, 원격 보존
- 완료: Society 내용 판본 확정; 완료의 의미: 저장 공간의 확정 주체가 기준 판본과 일관된 내용 스냅샷을 검증하고 새 공유 내용 판본으로 확정했다.; 이 완료만으로 보장하지 않는 것: 특정 원격 위치의 수신 또는 보존
- 완료: 원격 사본 전송·검증; 완료의 의미: 지정한 위치에서 지정한 판본을 수신하고 그 판본과 일치함을 검증했다.; 이 완료만으로 보장하지 않는 것: 이후 접근성, 별도 복구 지점, 더 새로운 작업의 보호

세 경계는 같은 체크 표시나 하나의 `synced` 값으로 합치지 않는다. 각 완료는
대상 자원·판본·위치와 완료 시각을 명시하며 확인 가능한 근거가 없으면 미확인으로
둔다. 전송·검증 등을 표현하는 작업의 수명과 관찰은 [공통 작업 모델](JobsAndOperations.md)을
따른다. 전문 앱의 저장 완료는 그 앱과 파일 시스템이 제공한 저장 계약 범위에서만
해석한다. 열린 데이터베이스나 여러 파일로 구성된 문서는 일관된 스냅샷을 제공할
수 있는 저장자·포맷의 협력이 필요하며, 일반 파일 복사만으로 트랜잭션 전체가
확정되었다고 말하지 않는다.

판본 확정 중 파일이 바뀌거나 스냅샷의 일관성을 확인하지 못하면 부분 내용을
확정하지 않고 작업 사본을 보존한다. 전송 중에 새 편집이 생기면 진행 중인 전송은
기존에 지정된 판본에만 적용한다. 이전 판본의 전송 완료가 새로운 작업 사본 또는
새 판본의 전송 완료로 바뀌지 않는다. 대상의 전송 실패, 검증 실패, 취소 및 재시도는
원본과 기존에 확인한 다른 사본의 상태를 덮어쓰지 않는다.

원격 검증은 확정 판본의 예상 해시·크기와 **대상**의 바이트를 재읽어 비교하거나,
대상에 대한 동등한 신뢰 가능한 무결성 증거를 확인하는 방식으로 수행한다. 어떤
방법과 시각으로 어느 판본을 검증했는지 기록한다. 단순한 업로드 요청 수락이나
전송 완료 응답만으로 검증 완료를 표시하지 않는다. 검증 당시의 일치 기록은 이후
접근 가능성이나 저장 서비스의 지속성을 무기한 보장하지 않는다.

## 독립적인 상태 차원

상태는 적어도 자원·요청한 판본·현재 기기·대상 위치·관찰 시각의 맥락에서
조회한다. 서로 다른 차원의 값은 동시에 존재할 수 있으며, 아래 값은 사용자에게
설명할 의미이지 단일 배타적 열거형을 강제하는 저장 스키마가 아니다.

- 차원: 현재 기기의 가용성; 구분할 내용: 프리뷰만 있음, 원본 없음, 다운로드 중, 원본 있음, 오프라인 유지; 판단 경계: 프리뷰와 원본을 분리한다. 오프라인 유지는 정책이고 원본의 실제 보유 여부·판본과 별도로 표시한다.
- 차원: 변경 상태; 구분할 내용: 변경 없음, 로컬 미반영 변경, 원격에 새 판본 있음, 충돌; 판단 경계: 기준 판본과 비교 대상을 밝힌다. 로컬 변경과 원격 변경은 동시에 존재할 수 있으며, 확인하지 못한 원격 최신 상태를 최신이라고 표시하지 않는다.
- 차원: 전송 상태; 구분할 내용: 대기, 전송, 검증, 완료, 재시도 필요; 판단 경계: 어느 판본을 어느 위치로 보내는지와 진행·오류를 표시한다. 완료는 해당 판본·대상에 대한 검증까지의 결과이다.
- 차원: 저장 위치 상태; 구분할 내용: 접근 가능, 연결 끊김, 권한 부족, 상태 미확인; 판단 경계: 위치별로 관찰한다. 접근 가능은 해당 판본 보유나 내용 검증을 뜻하지 않는다.
- 차원: 보존 상태; 구분할 내용: 이 기기에만 존재, 지정 사본 검증됨, 별도 복구 지점 있음; 판단 경계: 각 주장의 대상 판본과 위치·검증 시점을 명시한다. 복제본과 복구 지점은 별개이다.

프리뷰만 있을 때에는 원본을 즉시 열 수 있다고 표시하지 않는다. 원본이 로컬에
있더라도 사용자가 요청한 판본인지, 읽기 권한과 이를 열 수 있는 수단이 있는지는
별도로 판단한다. 오프라인 유지 설정만으로 다운로드와 검증이 완료된 것으로
표시하지 않는다. 원격 위치가 끊겼더라도 마지막으로 검증한 사실과 **현재 접근
미확인**을 분리한다. 장치 연결과 제공 저장소·기능의 관측은
[장치 상태와 기능 명세](DeviceStateAndCapabilities.md)를 따른다.

현재 기기에만 있다는 표현은 알려진 위치의 범위와 관찰 결과에 근거한다. 다른
위치를 조사하지 못했거나 목록이 불완전하면 확인된 사본이 현재 기기에만 있다고
표현하고, 다른 사본이 없다고 단정하지 않는다. 지정 사본이 검증되었다는 사실은
그 사본이 독립적인 복구 지점이라는 뜻이 아니다. 별도 복구 지점은 대상 판본과
보존 정책을 식별하며, 실제 복구를 시험했는지는 다시 구분한다. 내용 판본·휴지통·
복제·백업과 삭제 전파는 [복구와 보존 명세](VersionTrashReplicaBackup.md)를 따른다.

## 예시: 한 이미지와 여러 참조

다음은 설명을 위한 가상 예시이며 실제 저장소에 대한 관측이 아니다.

- 대상: 자원; 예시 상태: 이미지 `R` 하나. 이름과 경로는 `R`의 ID가 아니다.
- 대상: Mac Studio; 예시 상태: `R`의 현재 확정 판본 `C2`를 기준으로 하는 원본 작업 사본이 있다.
- 대상: 랩탑; 예시 상태: 이전 판본 `C1`의 캐시와 `C2`의 프리뷰가 있다. `C2` 원본은 없다.
- 대상: Society Cloud; 예시 상태: 공유용 `C1` 사본이 검증되어 있다. `C2`의 사본은 아직 확인되지 않았다.
- 대상: 프로젝트 두 개; 예시 상태: 각각의 프로젝트 관계가 같은 자원 `R`을 참조한다. 관계별로 최신 추적 또는 판본 고정을 정할 수 있다.
- 대상: Community 게시물; 예시 상태: `R`의 특정 판본 `C1`을 보여준다. `C2`가 만들어져도 게시물이 저절로 바뀌지 않는다.

이 경우 랩탑에서 `C2`의 프리뷰를 보는 것과 원본을 여는 것은 다르다. Mac Studio가
꺼져 있고 `C2` 원본이 다른 접근 가능한 위치에서 확인되지 않으면 랩탑은 `C2`를
가져올 수 있다고 보장할 수 없다. Cloud의 `C1` 검증 역시 `C2`의 원격 보존이 아니다.
이미지의 이름이나 위치가 바뀌어도 두 프로젝트와 게시물의 `R` 참조는 유지된다.

## 홈과 인스펙터 요구사항

홈에서는 각 자원의 현재 기기 열기 가능 여부, 요청 판본이 알려진 최신 판본인지,
해당 판본의 보존 상태와 진행 중인 전송을 빠르게 구분할 수 있어야 한다. 실제
근거가 부족하면 `확인 중` 또는 `미확인`을 표시한다. 프리뷰의 유무를 원본 사용
가능 표시로 재사용하지 않는다.

인스펙터에서는 자원 ID와 이름·표시 경로, 작업 사본 및 기준 판본, 확정 내용
판본과 메타데이터 이력, 위치별 보유 판본·접근·검증 시각, 전송 작업, 지정 사본과
복구 지점을 살필 수 있어야 한다. 로컬 저장 후 공유 확정 대기 중인 작업, 주 노드
연결 여부, 마지막으로 확인한 공유 판본과 충돌의 양쪽 내용도 구분한다. 판본에
연결된 미리보기·색인 등 후속 작업이 실패하면 그 판본과 실패 상태를 표시하고 해당
자원에서 재시도할 수 있어야 한다. [판본 이벤트와 후속 작업](JobsAndOperations.md#판본-이벤트와-후속-작업)을
따른다. 사용자가 위치를 선택하여 열기·다운로드·오프라인 유지를 요청할 때는 실제
권한과 해당 판본의 상태를 다시 확인한다. 위치 표시나 화면 탐색 자체는 내용 판본을
만들거나 파일을 수정하지 않는다.

## 기존 구현과 이행 경계

- iiFileProvider Catalog는 안정적인 파일 키, 포터블 동반 메타데이터와 일부 네이티브
  이동 재연결을 제공한다. 다만 기존 `importFile`은 복사본에 새 파일 키를 주며,
  알려진 키의 동반 파일 복사도 키를 분기한다. 이 동작을 그대로 다중 기기 자원
  복제의 동일 ID 보장으로 해석하지 않는다. [Catalog 계약](../../../SDK/iiFileProvider/docs/FILE_CATALOG.md)
- 현재 Catalog는 새 경로를 등록할 때 네이티브 파일 식별 정보가 같고 이전 경로가
  없으면 기존 키를 재연결한다. 이는 제한된 범위의 재연결이며, 식별자 재사용이나
  저장소 간 복사 등 모든 외부 이동에서 자원 연속성이 검증됐다는 뜻은 아니다.
  Catalog 키의 재연결만으로 관리 객체나 프로젝트 참조의 복구를 보장하지도 않는다.
  [구현](../../../SDK/iiFileProvider/src/Catalog/FileCatalog.cpp)
- iiFileProvider ObjectStore는 독립 키와 내용 판본, 메타데이터 이력 및 원본·편집본
  계약을 제공한다. 이 기능의 존재만으로 모든 Society 파일이 이미 해당 객체에
  등록되어 있거나 모든 과거 바이트가 보존된 것은 아니다.
  [ObjectStore 계약](../../../SDK/iiFileProvider/docs/OBJECT_STORE.md)
- iiSocietyContainer `FileRepository`의 관리 파일 자원 ID는 ObjectStore의 편집본
  객체 키이다. 수집된 파일의 온톨로지는 해당 섹션의 `society:catalogKey`도
  기록하지만, 두 키 자체가 같은 값은 아니다. Projects의 현재 `Files` 참조는
  컨테이너와 Catalog 키로 구성한 별도 식별자를 사용한다. 이 둘을 공통 자원 ID로
  서로 바꾸어 사용할 수 있다고 가정하지 않는다. 수집되지 않았거나 연결을 확인하지
  못한 항목은 미확인으로 남기며, 이름·경로·내용 해시만으로 연결하지 않는다.
  [관리 파일 계약](../../../SDK/iiSocietyContainer/docs/ManagedFiles.md),
  [Projects 계약](Projects.md)
- 이전 경로의 관리 객체가 이미 tombstone 처리된 뒤 새 경로가 다른 객체로 수집된
  경우, 현재 재조정만으로 두 객체가 자동으로 같은 ID가 되지는 않는다. 두 기록과
  기존 참조를 보존하고, 확인되지 않은 관계를 파일명이나 내용 해시만으로 병합하지
  않는다. 경로 이동 기록과 각 객체의 이력을 함께 검토할 수 있는 별도 복구가 필요하다.
- 현재 Projects는 프로젝트 안의 리소스 관계 ID와 경로 또는 외부 식별자를 저장한다.
  새로 선택하거나 명시적으로 편집한 `Files` 참조에는 동일 컨테이너 Catalog 키를
  연결하므로 같은 파일을 참조하는 두 프로젝트에서 이 한정된 자원 ID를 공유한다.
  `Files` 밖의 기존 참조, 다른 섹션·기기·복제본 및 게시물까지 전역 식별이
  연결된 것은 아니다. 패키지 참조와 포함 파일의 현재 동작은 [Projects 문서](Projects.md)를 따른다.
- 현재 Helper Sync는 호스트가 확정한 경로별 리비전, 작업 상태 및 일부 제공자별
  판본 배치를 다룬다. 문서화된 현재 동작은 오래된 기준의 파일 편집에서 호스트
  상태를 유지하고 다른 내용을 충돌 사본으로 보존하며, 삭제 충돌에서는 호스트의
  확정 상태를 따른다. 이것이 이 명세의 자원 ID 기반 충돌 기록·알림·양쪽 판본
  보존과 해결 UI 전부가 구현되었다는 뜻은 아니다. 일반 파일 단위 복제이며 모든
  과거 바이트나 다중 파일의 원자적 스냅샷을 보장하지 않는다. 집계형 동기화 상태는
  이 문서의 자원별 다차원 상태를 대체하지 않는다. [동기화 문서](Synchronization.md),
  [Namespace 계약](../../../SDK/iiSocietyHelper/docs/Sync/Namespace.md),
  [스냅샷과 상태](../../../SDK/iiSocietyHelper/docs/Sync/Snapshots.md)
- 기존 프리뷰와 인스펙터가 표시하는 실제 범위는
  [파일 정보 문서](FilePresentation.md)를 따른다. 이 문서의 모든 상태와 제어가
  현재 화면에 구현되어 있다는 의미가 아니다.

이행할 때는 기존 Catalog 키, ObjectStore 키, 프로젝트별 리소스 ID와 동기화 경로를
각 소유자의 범위와 의미에 맞게 조사해 연결한다. 어느 기존 키를 공통 자원 ID로
재사용할지 또는 별도 매핑을 둘지는 충돌·기기 간 이동·복사 의미를 확인한 후
결정한다. 기존 데이터에서 과거 판본, 원격 사본이나 검증 이력을 추측해 만들지
않는다. 식별이 모호한 항목은 원본과 기존 참조를 보존하고 검토 가능한 상태로 둔다.

## 구현 시 수용 검증

1. 자원 이름과 확인된 저장 위치를 변경해도 자원 ID와 두 프로젝트의 참조가 유지된다.
2. 같은 바이트의 독립 자원은 별도 ID와 권한을 유지하고, 명시한 사본은 원래 자원과
   지정 판본에 연결된다.
3. 메타데이터만 변경하면 내용 판본과 내용 전송 완료 상태를 새로 만들지 않는다.
4. 전문 앱의 저장, Society 판본 확정, 대상 사본 전송·검증을 각각 독립적으로
   성공·실패시켜도 다른 완료를 잘못 표시하지 않는다.
5. 전송 중 재편집, 검증 실패, 재시작 및 재시도에서 각 작업의 판본과 기존 바이트를
   보존하며 오래된 완료가 새 편집을 보호 완료로 만들지 않는다.
6. 프리뷰만 있는 기기, 원본이 있는 기기, 오프라인 유지 요청 중인 기기의 열기
   가능성과 원본 보유 상태를 구분한다.
7. 최신 호스트나 저장 위치가 연결되지 않았을 때 최신·접근·보존 여부를 추측하지
   않으며 마지막 검증 사실과 현재 미확인을 함께 표시한다.
8. 서로 다른 기준에서 로컬과 원격이 바뀌면 충돌을 드러내고 양쪽 내용을 보존한다.
9. Cloud의 이전 판본 검증을 현재 판본의 보존으로 표시하지 않고, 검증된 사본과
   별도 복구 지점 및 복구 시험 결과를 구분한다.
10. 두 프로젝트와 판본이 고정된 게시물에서 자원 이동 이후에도 올바른 자원과
    지정 판본을 참조한다. 목록·인스펙터 탐색은 파일이나 판본을 변경하지 않는다.
11. 같은 기준으로 출발한 두 기기의 바이너리 편집을 반대 순서로 제출해도 두 내용과
    기준·확정 관계가 보존되고, 뒤늦은 제출이 먼저 확정된 내용을 덮어쓰지 않는다.
12. 판본 비교 이후 다른 기기가 먼저 확정하면 적용 시점에 다시 충돌로 처리한다.
    응답 유실 후 같은 제출을 재시도해도 중복 확정하지 않는다.
13. 주 노드 연결이 끊긴 동안 작업을 저장하고 기기를 재시작한 뒤에도 기준과 내용이
    남는다. 재접속 전에는 공유 확정으로 표시하지 않고 재접속 후 비교·조정한다.
14. 주 노드에서 오프라인 확정한 판본과 다른 기기의 미수신 상태, 원격 검증 여부를
    따로 표시한다. 주 노드 부재 시 다른 복제본이 자동으로 확정 주체가 되지 않는다.
15. 삭제와 내용 수정의 경합, 저장 공간 부족, 지원하지 않는 바이너리 병합 및 해결
    중 추가 변경에서 양쪽 작업을 보존하고 실패나 충돌을 사용자에게 표시한다.
16. Projects와 컨테이너가 서로 다른 기존 식별자를 사용하는 경우에도 검증된 관계를
    명시적으로 연결한다. 연결할 근거가 없으면 기존 참조를 유지하고 미확인으로 둔다.
17. 메타데이터 또는 미리보기만 허용된 주체는 허용되지 않은 원본을 읽거나 내려받을
    수 없다. 원본 보유 여부와 미리보기 접근 권한도 별도로 표시한다.
18. 새 내용 판본 작성과 프로젝트 구성 수정이 허용되어도 권한 부여·변경이나 게시물
    공개 권한이 없으면 해당 행위를 할 수 없다. 생성된 결과도 자동으로 공개되지 않는다.
19. 만료·철회된 부여와 확인할 수 없는 부여는 유효한 권한으로 취급하지 않는다.
    대기 중인 작업은 수행·외부 공개 시 필요한 권한을 다시 확인한다.
20. 역할이 같은 두 주체라도 대상·범위·기간이 다르면 유효한 행위가 다를 수 있다.
    저장 위치의 목록·읽기·쓰기·전송과 정책 변경은 각각 확인한다.
21. 이름 변경과 확인된 저장소 이동은 자원 ID·프로젝트 참조와 해당 내용 판본을
    유지한다. 내용 변경을 확정하면 같은 자원에 새 내용 판본을 기록한다.
22. Society 밖에서 같은 파일시스템 내 이동을 관찰했을 때 연속성이 충분히 확인되면
    기존 자원과 사본 위치를 연결하고 그 근거를 남긴다. 색인 재등록 여부와 실제
    파일 가용성도 각각 확인한다.
23. 파일시스템 식별자 재사용, 하드 링크, 파일 교체, 다수 후보 또는 부분 스캔으로
    이동 여부가 모호하면 같은 이름·해시나 이전 경로의 부재만으로 자원을 합치지
    않는다. 원래 기록과 참조 및 발견된 파일을 보존한다.
24. 다른 저장소로 옮길 때 대상 판본의 게시·검증과 기존 위치의 제거를 따로 기록하며,
    대상 오류나 기존 위치 미확인을 이동 완료·보존 완료로 표시하지 않는다.

## 정리 계획과 자동 삭제 경계

`cleanup_plan`은 선택된 컨테이너의 `Files` 또는 `Models` 파일에 대해 마지막으로 관찰된 자원·판본과 저장된 직접 관계를 읽고 결정론적 정리 정책의 근거와 보류 사유를 반환한다. 관계의 유형은 그대로 표시하며 관계가 없다는 사실을 모든 프로젝트의 종속성이 없다는 증거로 바꾸지 않는다. 알려진 관계, 불완전한 관계 관찰, 미확인 대상, 미확인 종속성 범위와 검증되지 않은 복구 가능성은 각각 구별한다. 원본을 Deleted로 옮기기 전에는 이 계획만으로 복구가 가능하다고 판정하지 않으며, 현재 계획은 실행 권한이나 승인 토큰이 아니다.

정책은 대상의 현재 관찰, 전체 종속성 범위, 알려진 관계의 검토 및 복구 가능성 근거를 모두 충족한 경우에만 사용자 승인 단계에 이를 수 있다. 현재 수집기는 전체 종속성과 복구 가능성을 검증하지 못하므로 자동 정리는 항상 보류한다. 에이전트와 헤드리스 클라이언트의 `trash`, `remove` 및 Deleted로 향하는 `move`는 데몬에서 거부하고, 사용자가 Society 화면에서 직접 요청하는 기존 작업은 유지한다. 헤드리스 영구 삭제나 자동 정리의 실행·승인 경로는 아직 제공하지 않는다.

데몬의 화면 구분은 운영체제가 제공한 로컬 피어와 실행 파일 경로에 근거하며 사람의 신원이나 클릭 자체를 암호학적으로 인증하지 않는다. 직접 화면 작업의 확인 절차는 해당 화면이 담당한다. 이 경계는 에이전트의 승인된 실행 계획, 파일 내부 참조 검사 또는 외부 프로세스의 파일 변경을 대체하지 않는다.
